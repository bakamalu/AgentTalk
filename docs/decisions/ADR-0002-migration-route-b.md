# ADR-0002：迁移采用路线 B（免小号、窗口式可回滚）

- 状态：**已接受**
- 日期：2026-10-30
- 关联：[`../04-migration-snowluma.md`](../04-migration-snowluma.md)

## 背景

从 NapCat 迁移到 SnowLuma，要求不回归任何已有修复。两种灰度形态：

- **路线 A（真并行）**：测试小号 + 第二个 QQ 实例 + 第二套 Koishi，生产不动。
- **路线 B（窗口式）**：不开小号，用"冷启动演练 → 试切 → 正式切"三次可回滚窗口。

## 关键约束（决定了路线 A 的成本）

1. **同号不能双跑**：NapCat 与 SnowLuma 都是注入式，且同号两地登录互踢。
   真并行必须有第二个 QQ 号 + 第二个 QQ 实例（Linux 多开需 `--user-data-dir` + 独立 Xvfb）。
2. **同群双 bot 会污染插件状态**：状态键不含 botId，`groupBuffer` 先取先删、
   `activeUntil` 会被任一 bot 点亮。
3. **源码构建拿不到原生注入层**：`wrapper.linux.node` 只随官方发行包分发，
   `pnpm build` 产不出。制品的正确形态是"发行包原生层 + fork 编译的 JS 层"。

## 决策

采用**路线 B**，并把风险拆成三次窗口：

| 窗口 | 时长 | 烧掉什么风险 | 生产影响 |
|---|---|---|---|
| W0 冷启动演练 | 0.5 天 | 安装/配置/端口/启动参数 | 无（不注入 QQ） |
| W1 试切 | 15 分钟 | **能否注入现有 QQ、是否需要重新扫码** | 可回滚 |
| W2 正式切换 | 10 分钟 | 协议行为（发送/引用/撤回/媒体段） | 可回滚 |

## 放弃路线 A 的理由

- 需要额外 QQ 号，且 Linux 双实例可用性未验证；
- 即便并行，也**无法验证"注入现有 QQ 客户端"**这个最大不确定项——那必须真停一次；
- 路线 B 少 1~2 天工作量，风险通过"W1 先试"来控制。

## 前置条件（不可跳过）

1. `NAPCAT_WS_TOKEN` 在 NapCat / Koishi 两侧统一（否则 W2 必须改配置重启，窗口翻倍）；
2. 一键切换/回滚脚本**提前写好并 dry-run**，不在窗口里现场写代码；
3. 制品必须校验 sha256（要注入 QQ 的二进制，不能放行未校验文件）；
4. `state/deepseek` 全量备份。

## 后果

- 生产会有三次短暂中断（W1 一次 15 分钟、W2 一次 10 分钟）；
- NapCat 资产长期保留，不因"迁移成功"而删除；
- 守护脚本需长期保留 `BOT_GATEWAY=napcat|snowluma` 开关。
