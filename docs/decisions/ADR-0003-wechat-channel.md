# ADR-0003：微信通道选型（默认企业微信，个人微信缓议）

- 状态：**提议中**（待需求方回答 `docs/07-wechat-bot.md` 第 8 节的三个问题后定稿）
- 日期：2026-11-02
- 决策者：项目 owner（待定）

## 背景

AgentTalk 需要引入微信机器人。个人微信无官方 API，合规入口只有企业微信/公众号；
协议模拟与 hook 方案均有封号风险。同时现有部署"全绑回环、不暴露公网"，
与企微自建应用的 Webhook 回调要求存在冲突。详细对比见 `docs/07-wechat-bot.md` 第 2 节。

## 备选项

| 方案 | 说明 |
|---|---|
| A. 企微·自建应用 + 官方 `@koishijs/plugin-adapter-wecom` | 零业务代码改动即可 PoC，但需公网 HTTPS 回调 |
| B. 企微·智能机器人长连接 + 自研 adapter | 不开公网端口、原生群聊@语义，需 ~1-2 周开发 |
| C. 个人微信 Wechaty + padlocal | 真正的"微信号"形态，但违反使用规范、有服务费、社区 adapter 维护弱 |
| D. 本机 hook（Xbot/wxhook 等） | 与 Linux headless 部署体系冲突，封号风险最高 |
| E. Gewechat 等旧协议框架 | 上游已停止维护，直接排除 |

## 决策（提议）

**先 A 后 B，C 缓议，D/E 排除。** 理由：

1. A 复用 Koishi 官方 adapter，与"换网关不动插件"的分层原则一致，PoC 成本最低；
2. B 是目标形态：长连接模型与现有安全策略（回环绑定、无公网服务面）完全兼容，
   且智能机器人天然支持群聊 + @，与 `deepseek.js` 的唤醒语义对齐；
3. C 的收益（个人号形态）与风险（封号、供应商依赖、adapter 停更）不对称，
   仅在需求方**明确接受风险并确认需要个人号**后另行立项；
4. A→B 过渡期间业务层改动（`PLATFORM_CAPS`、名单命名空间、图片路径）两方案通用，不浪费。

## 后果

- 需要为方案 A 开一条最小暴露面的 HTTPS 反代（只放行回调路径），并补 s0 断言；
- 若最终走 B，需新增 `plugins/adapter-wecom-robot.js` 并纳入 watchdog 巡检；
- 业务层需按 `docs/07-wechat-bot.md` 第 4 节完成平台差异收敛，OneBot 侧行为保持不回归；
- 若未来引入个人微信（C），本 ADR 需新增修订记录而非推翻（A/B 结论对企微侧仍成立）。
