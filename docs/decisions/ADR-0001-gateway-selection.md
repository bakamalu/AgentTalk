# ADR-0001：网关层选型（NapCat 保留，SnowLuma 作为迁移目标）

- 状态：**已接受**
- 日期：2026-10-30
- 决策者：项目 owner

## 背景

需求是"把 QQ 群聊接入大模型"。QQ 没有官方机器人 API，必须借助**协议端**（把 QQ 客户端会话
转换成 OneBot v11）。当前生产使用 NapCat，社区另有 SnowLuma 等实现。

## 备选项

| 方案 | 说明 |
|---|---|
| A. 保持 NapCat | 已稳定运行，19 项修复全部基于它验证 |
| B. 换 SnowLuma | 协议实现更"正统"、自带 SDK/MCP/多账号/SQLite 消息库 |
| C. 换 Lagrange / go-cqhttp 等 | 生态活跃度或 QQ 版本支持不足 |
| D. 不用协议端，改 Telegram/微信 | 需求明确要求 QQ 群 |

## 决策

**A 保留为生产，同时准备 B。** 理由：

1. 两者**同层**（都是注入式协议端），SnowLuma 不能替代 Koishi；
2. 业务层只依赖 OneBot v11 语义，具备**换网关不动插件**的条件；
3. SnowLuma 的增量价值（SDK/MCP/多账号）当前项目均未使用，收益不足以承担迁移风险；
4. 但 NapCat 在 `message_id` 语义、引用/撤回可靠性上存在长期隐患，需要一条可走的退路。

## 后果

- 必须把"网关契约"（见 `docs/01-architecture.md` 第 2 节）显式写下来并做回归验证；
- 迁移时必须保留 NapCat 全量资产以便回滚；
- SnowLuma 的**非商业许可**需在商业化前重新评估。
